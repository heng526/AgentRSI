# 重新审视 Agent Harness 进化的评测方法
# Rethinking the Evaluation of Harness Evolution for Agents

## 二、一句话总结

现有 harness 进化方法普遍"用单元测试反馈搜索 harness 配置、再在同一个公开基准上报告最终成绩"，本文指出该协议混淆了两件事，并在统一预算协议下把 harness 进化与两类简单的测试时扩展（并行采样、顺序精化）对比：结果显示 harness 进化在有无单元测试两种设定下都**不能稳定超过简单的测试时扩展基线**，且当搜索任务与评估任务不相交时增益几乎消失（平均仅 +0.6 分）——现有 harness 进化证据应被谨慎解读。

## 三、研究问题与动机

**背景**：LLM agent 越来越依赖外部 harness（定义提示、工具、记忆、校验例程与控制逻辑的外层）与环境交互。harness 工程在固定模型下就能显著影响性能，但传统上是手动的：开发者检查轨迹、诊断失败、修订 harness。这催生了**自动 harness 进化**：分析先前轨迹/分数/失败 → 提议修改 → 在基准任务上评估 → 循环。

**对现有评测协议的两个根本性质疑**：

1. **缺少测试时扩展对照**。harness 进化本身就是一个迭代搜索过程，反复用任务反馈评估并修订候选 harness——这与 agentic 测试时扩展（test-time scaling）在结构上同构。那么它的收益究竟来自"harness 设计更好"，还是仅仅来自"在评估任务上额外花了搜索算力"？不与并行采样、顺序精化等简单基线在**匹配的反馈与推理预算**下对比，就无法回答。
2. **搜索与评估共享同一基准导致过拟合风险**。搜索所用任务与最终报告成绩的任务重叠时，观察到的增益可能反映对特定任务样例的适应，而非可迁移的 harness 设计改进。

**核心问题**：harness 进化带来的是可泛化的 harness 设计改进，还是主要是重复采样的效果？

## 四、方法详解

### 4.1 统一记号与预算视角

π_θ 为 agent 策略，x ~ X 为任务。用 harness h 执行 agent 产生轨迹 y ~ π_θ(· | x; h)。当单元测试 g 可用时定义结果 R(y, g) ∈ {0, 1}。**每个方法都消耗同样的计算预算 K**，为每个任务返回最终轨迹 ŷ。另定义摘要映射 Φ（由与策略相同的底层模型实现）：把经验存储摘要为下游 agent 可消费的形式（复发性失败、冗余尝试、成本等），供后续精化/编辑步骤诊断与避免重复编辑。

### 4.2 四种对比方法（对应 Figure 2 的统一框架）

**(a) 并行采样（Parallel Sampling，测试时扩展：宽度）**。用固定 harness h 独立抽 K 条轨迹 y_1..y_K ~ π_θ(·|x;h)。无单元测试时靠模型自评：ŷ = argmax_{k≤K} J(y_k)，J 为 agent 自身实现的自评裁判；有单元测试时直接选通过者：ŷ ∈ {y_k : R(y_k,g)=1}。

**(b) 顺序精化（Sequential Refinement，测试时扩展：深度）**。第一条 y_1 ~ π_θ(·|x;h)，之后每条以上一条为条件反思修订：无单元测试时 y_k ~ π_θ(· | x, Φ(y_{k−1}); h)，返回 ŷ = y_K；有单元测试时同时暴露轨迹与其结果 y_k ~ π_θ(· | x, Φ(y_{k−1}, R(y_{k−1},g)); h)，返回任何通过者。

**(c) Harness 进化（Harness Evolution，共享进化 harness，跨任务）**。保留顺序精化的迭代循环，但把预算花在策略**周围的 harness** 上，并在任务分布上优化而非拟合单任务。抽一批任务 {x^(i)}_{i=1..n} 初始化经验存储 C_0；第 k 轮在当前 harness 下每任务采 m 条 rollout，把证据 e_k = (h_k, {y_k^(i,j)} [, {R(y_k^(i,j), g^(i))}]) 并入存储；**元 agent M** 读取摘要 Φ(C_{k−1}) 产出下一 harness：h_k = M(Φ(C_{k−1}))，k=2..K，从种子 harness h_1 出发。搜索目标是对任务分布（或留出分布）的期望成功：h* = argmax_h E_{x~X}[R(y,g)]。无单元测试时取最进化者 ĥ = h_K；有单元测试时取聚合结果最高者 ĥ = argmax_k R̄(h_k)。最后用 ĥ 为目标任务采样 ŷ。**实例化**：采用 AHE（Agentic Harness Engineering, Lin et al. 2026），但**禁用其 explore agent**——因为 explore agent 会从外部检索针对该基准调好的 harness，把"可复用的进化"与"检索已拟合评估任务的现成解"混为一谈；禁用后所有增益都可归因于反馈信号上的进化。

**(d) Harness 缩放（Harness Scaling，本文提出的任务级类比，任务专属进化 harness）**。作为 harness 进化的"harness 层测试时扩展"类比：对**单个评估实例**分配额外推理预算做 harness 修订（instance-guided adaptation，对照 dataset-guided evolution）。从 h_1 出发每任务采 y_1 ~ π(·|x;h_1)，观察轨迹后由元 agent 更新 harness 并在新 harness 下重采：h_k = M(x, Φ(h_{k−1}, y_{k−1}))，y_k ~ π_θ(·|x;h_k)，k=2..K；有单元测试时更新还以 R(y_{k−1},g) 为条件。四者的区别被压缩为三个正交维度：**接收什么反馈、如何花预算、修改的是轨迹还是 harness**。

### 4.3 实现与公平性细节

- **基准**：Terminal-Bench 2.1（Terminal-Bench 2.0 的核验修订版：修复 89 任务中的 28 个——外部依赖漂移、资源预算错配、指令与测试不对齐——保持 89 个终端任务）。沿用 Meta-Harness/AHE/AEVO 的选择。
- **模型**：Claude Opus 4.6、GPT-5.4、GPT-5.4 mini；每模型最高 128k 生成 token、high reasoning effort；所有结果为**两次独立运行平均**以降低随机方差。
- **公平性**：四种方法都从**同一个初始 harness** h_1 出发——即 AHE 使用的初始 harness，且它就是一个极简 harness：模型只有一个 bash 工具，无技能、无中间件、无持久记忆；该 harness 同时作为并行采样与顺序精化的固定 harness。AHE 取 m=1（每 harness 每任务一条 rollout）以匹配 rollout 预算；统一预算 K=5。每个 rollout 在独立新建的 E2B 远程沙箱执行；沙箱崩溃/API 超时等基础设施异常**计为 r=0** 而非剔除。
- **指标**：pass@1 定义为所有 rollout 上的平均奖励（公式 1，即 avg@k 口径）；pass@k 为至少一条 rollout 解决的任务比例（公式 2），仅在单元测试可用设定下报告，其与 pass@1 的差距反映 agent 跨独立尝试的方差。
- **摘要器**：采用 AHE 框架的 Agent Debugger——把每条轨迹的消息组织为可导航的文件环境，按查询分组轨迹，要求找出每次失败的根因或成功的模式，产出带 pass/fail 标注的任务级分析报告并聚合为基准级概览，原始轨迹保留可查证，通过渐进式披露控制 token 消耗。

## 五、实验与主要结果

**设定一：无单元测试（Table 1 / Figure 1，pass@1）**。

| 方法 | Opus 4.6 | GPT-5.4 | mini | 平均 |
|---|---|---|---|---|
| 直接采样（初始 harness） | 69.9 | 75.3 | 59.4 | 68.2 |
| 并行采样 | 74.7 | 79.2 | 62.9 | **72.3** |
| 顺序精化 | 73.0 | 73.0 | 61.8 | 69.3 |
| Harness 进化 | 71.4 | 69.7 | 61.3 | **67.4** |
| Harness 缩放 | **76.0** | 78.1 | 61.2 | 71.8 |

关键发现：(1) 并行采样最稳定，三模型全部提升（68.2→72.3）；(2) **harness 进化平均低于直接采样基线**——GPT-5.4 从 75.3 骤降至 69.7，说明仅靠 agent 自我判断引导的迭代 harness 修订会**主动伤害**强模型；(3) harness 缩放在 Opus 上拿到最佳单点 76.0、平均 71.8 具竞争力；(4) 顺序精化平均仅 +1.1 且使 GPT-5.4 轻微退化。结论：缺乏外部正确性信号时，强 agent 也难以从自身轨迹可靠提取 harness 修订信号；自生成反馈噪声大、顺序修订有复利早期错误的风险。

**设定二：有单元测试（Table 2，pass@1 / pass@5）**。

| 方法 | Opus p@1 | GPT-5.4 p@1 | 平均 p@1 | 平均 p@5 |
|---|---|---|---|---|
| 直接采样 | 69.9 | 75.9 | 72.9 | – |
| 并行采样 | 84.8 | 87.1 | **86.0** | 86.0 |
| 顺序精化 | 83.1 | 85.4 | 84.3 | **91.8** |
| Harness 进化 | 73.0 | 78.6 | 75.8 | 86.2 |
| Harness 缩放 | 83.1 | 82.0 | 82.6 | 89.3 |

单元测试反馈让所有方法大幅超过直接采样，但 harness 进化与缩放在两个指标上都不超过更简单的基线：pass@1 上 harness 进化仅比直接采样高约 3 分（75.8 对 72.9），远低于并行采样的 86.0；pass@5 上顺序精化最强（91.8 对 86.2 / 89.3）。作者给出关键推理：**如果 harness 修订真的产出更好的 harness，改进应体现在 pass@1 上**（用进化出的 harness 一次尝试就该更好）；而实际收益只有在多条轨迹中做选择时才出现——说明现有 harness 进化的收益主要来自"多试几次"，而并行采样与顺序精化能更直接、更有效地获得同样效果。精化解法是比修订 harness 更划算的算力用途。

**设定三：不相交搜索/评估任务的泛化（Table 3）**。把 Terminal-Bench 2.1 划为 45 训练 / 10 验证 / 34 留出测试：在训练集上带单元测试跑 harness 进化、按验证集选最优 harness、在测试集报告 pass@1。结果：Opus 63.3→64.5（**+1.2**）、GPT-5.4 72.1→72.1（**+0.0**）、平均 67.7→68.3（**+0.6**）——与在同批任务上评估时的提升形成鲜明对比。其余三种方法在此设定不适用（它们产生的是轨迹而非可复用工件）。结论：进化中发现的修订编码的是**任务特定捷径**而非更好的 harness 设计原则，泛化能力有限、严重过拟合训练任务。

## 六、消融与分析（修订内容与任务属性的定性分析）

1. **Harness 进化的修订模式（5.1 节）**：元 agent 的修订是"理性且有据的"——第一动作通常在**提示层**（往系统提示与长期记忆加行为规则：更高预算意识、尽早产出交付物、改动前复制易碎状态、结束前复查任务约束）；当咨询性文本到达平台期后升级到**中间件层的运行时强制**（轮次预算追踪器、超长工具输出截断、交付物缺失或未验证时阻止完成的 finalization gate）；还会改**工具层**（纠正误导性工具说明、在命令执行时注入恢复提示）。
2. **Harness 缩放的修订模式**：主流模式是把此前 rollout 中**特定失败的知识**编码进下一轮提示/长期记忆——记录已知 bug、实现模板、校验检查、文件路径、命令序列；另一大类是**工作流效率**（把重复轮询、探索性命令、缓慢安装换成紧凑命令计划：批量安装与验证、跳过不必要的环境探测、放宽慢安装的 shell 超时、规定显式消息预算）；第三类是**强化验证行为**（提交前加语法检查、单元测试或模仿验证器的本地检查，案例见附录 B：caffe-cifar-10 后台安装+避开轮询、cancel-async-tasks 加 t.cancelling() 守卫与"不许弱化测试"规则、compile-compcert 直装 Coq 8.16.1 并调整 make install 顺序、db-wal-recovery 禁止备份前打开 SQLite、mteb-retrieve 为查询与段落用不同 PromptType）。
3. **为什么修订广却收益有限——核心诊断**：大多数编辑是**记住修法（memorize fixes）而非蒸馏策略（distill strategies）**。这些信息多数是胜任的 agent 在单条 rollout 内通过探索就能重新发现的，持久化进 harness 只是在 agent 本已能解的任务上省时间，很少把失败转化为成功；来自深层领域推理需求或 harness 控制范围之外的约束的**稳定硬失败核**不受积累知识影响；而持续膨胀的提示文本带来**上下文膨胀（context bloat）**，可能抵消剩余收益。
4. **两个补充解释（5.2 节）**：(a) agent 在 Terminal-Bench 上得分已较高，剩余失败可能源于底层模型局限而非 harness 缺陷；(b) Terminal-Bench 可能对 harness 设计**本身不敏感**——一个 shell 工具加基本提示的极简配置已足以完成多数可解任务，性能瓶颈在模型推理而非脚手架。由此提出 harness 进化的价值是**任务依赖**的，未来应在满足两个条件的基准上研究：(1) 任务足够难、留有大量改进空间；(2) 性能强依赖 harness（专用工具、技能或工作流对成功至关重要）——此时更好的 harness 才能切实扩大 agent 可解问题的集合。

## 七、局限性与批判性评述

1. **被检验对象单一**。实验只实例化了 AHE（且禁用 explore agent）一种 harness 进化算法；Meta-Harness、AEVO 等被点名的方法并未实测。结论"现有 harness 进化不过测试时扩展"严格来说只对 AHE 变体成立。特别值得注意的是，**记忆型进化方法（如 Recuris、Memento、Experience 类）未被纳入对比**——这类方法的可迁移证据（论文1在 86 个留出任务上 +9~+17.44）与本论文的负结果如何调和，文中未讨论。
2. **预算设定偏向小规模**。K=5、m=1、单一极简种子 harness（只有 bash）；部分已发表方法用更大的搜索预算、更丰富的种子 harness 与多轮门控（如论文1的验证门 + 锚点任务 + 预注册划分）。小预算下得出的"进化不如采样"可能是**预算区间依赖**的结论。
3. **基准选择内嵌了结论**。作者自己承认 Terminal-Bench 对 harness 设计不敏感、基线已高（GPT-5.4 直接采样 75.3）。在一个"harness 无关紧要"的基准上得出"harness 进化无用"的结论存在一定程度的自证；作者也把"寻找 harness 敏感的基准"留作未来工作，这等于承认本文的实证范围受限。
4. **pass@1 口径非标准**。本文 pass@1 实为所有 rollout 的平均奖励（avg@k），与文献中常用的无偏 pass@1 估计量不同；虽然内部对比公平，但与其他论文数字不可直接比较。
5. **两次运行平均的方差控制较弱**。论文1的附录显示 Terminal-Bench 上同配置重跑差异可达 5.7 点；本文无置信区间或显著性检验，+0.6、+1.2 这类差值的解读（"无显著增益"）缺少统计支撑。
6. **泛化实验的划分未做领域平衡说明**，34 个测试任务的代表性未知；且 harness 进化未在验证集上做模型选择之外的早停/回滚等机制（对比论文1的门控设计），负结果部分反映的是"朴素进化协议"的失败。
7. **正面价值**：尽管有上述限制，这篇论文的贡献在于把"harness 进化 vs 测试时发现"这一混同明确化，其四方法统一预算形式化（修改轨迹 vs 修改 harness、共享 vs 任务专属）是可复用的评测框架；其"收益应体现在 pass@1 而非仅 pass@k"的论证是检验任何进化方法的重要思想实验。

## 八、对读者研究的启发

读者做"多模态 Agent 长时程记忆 + 递归自改进 RSI / harness 进化"研究，这篇论文是**必须正面回应的对手方**，启发与缺口如下：

1. **评测协议层面（最直接的借鉴）**：任何 RSI/harness 进化工作都应内置三组对照——(a) 匹配反馈与推理预算的并行采样与顺序精化基线；(b) 搜索/评估任务不相交的留出评估（train/val/test 三分）；(c) 收益机制分解（pass@1 vs pass@k：增益若只在多次选择后出现，说明是"多试"而非"更好的设计"）。论文1 的测试时适应分解（重试 +26.4 对适应 +2.3）与论文2 的匹配 token 对照（AKS-90）都是对这类质疑的部分回应，说明该批判已实际改变了领域标准。
2. **"记住修法 vs 蒸馏策略"是进化设计的第一性检验**：本文的诊断（编辑多为任务特定捷径、硬失败核不动、上下文膨胀抵消收益）给出了明确的反模式清单。读者的多模态记忆系统应避免把"单次探索可重新发现的事实"持久化，而应蒸馏跨任务策略；并显式度量"硬失败核"是否被触动。
3. **反馈信号质量决定修订质量**：无单元测试时自评反馈使 harness 进化反而伤害强模型（GPT-5.4 −5.6）。多模态场景往往缺乏精确验证器，这提示：进化循环需要**外部可验证信号**（工具回执、程序化 verifier、跨模态一致性检查），或引入论文1式的验证门控与锚点回归检验来过滤噪声修订。
4. **与本组另两篇论文的三角关系值得写进相关工作**：论文3 是对论文2（自由程序搜索、点估计晋升）式协议的正面批判，论文2 以留出集与跨基准迁移回应；论文1 以门控+预注册划分+预算匹配对照+诚实分解回应。三者共同勾勒出当前 RSI 评测的方法学前沿；读者可系统比较三者协议差异（预算匹配、划分方式、统计检验、成本核算）作为自己论文的实验设计基础。
5. **研究缺口**：(a) 在"harness 敏感"基准（任务难、专用工具/技能/工作流关键）上重做本文对比——多模态长视频/长文档理解可能是天然场所（论文2 的 oracle 分析显示 K=40 处均匀采样与 oracle 差 21.1 分，上下文构造明显 bind 性能）；(b) 把记忆型进化（Recuris/Memento 一类）纳入测试时扩展对照，检验"跨任务可复用记忆"是否比"任务级 harness 搜索"更接近真正的设计改进；(c) 为负结果补统计功效（本文无 CI）；(d) 上下文膨胀的定量刻画与剪枝机制的收益；(e) 混合策略的系统研究——何时把算力花在任务级采样、何时花在跨任务 harness/记忆进化（本文与论文2 分别代表两端，缺一个统一的资源分配理论）；(f) 多模态验证器缺失场景下的"弱验证进化"协议设计。
