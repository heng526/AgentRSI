# Robot 已有答案评分准备清单

范围：只核对本地代码、已有归档及 node01 上两次已完成运行的只读证据。没有调用 judge/API、生成答案、运行评分、重嵌入或推理；以下不含准确率结论。

## 1. 已有答案能否可靠关联到标注？

可以按 `(video_id, id)` 关联。两个归档各有 1,276 行、1,276 个唯一问题 ID；均无重复或未知 ID。与 `robot.json` 对照时，1,276/1,276 行的问题 ID、视频 ID、问题文本及复制的参考答案均匹配。记录字段包含 `id`（question_id）、`video_id`、`question`、`answer`（参考答案）、`response`（模型回答）；标注字段还包含 `reasoning`、`timestamp`、`type` 等。当前证据未发现可据以直接报告的评分标签。

## 2. 现有 judge 按什么规则工作？

共享 prompt 询问：结合问题上下文，模型回答能否逻辑推出参考答案；语义等价也算正确，要求只输出 Yes/No。代码中有两种 evaluator：

- Azure：默认部署配置为 `gpt-4o-2024-11-20`（也可由环境配置）；空回答直接记 `False`。其余回答中只要响应小写后包含 `yes` 子串即记 `True`，否则记 `False`。捕获异常后返回 `False`；请求循环最多尝试 20 次，循环内会等待。该兜底会把 API 故障与真实错误答案混在一起。
- GLM：空回答直接记 `False`；温度为 0，最多 512 token，超时 60 秒。用第一个完整单词 `yes`/`no` 判定；找不到时返回 `None`。该函数没有重试包装。默认配置涉及 GLM-5.3-Flash 与 `embedding-3` 等服务名，但本次没有验证服务可用性或发起请求。

两种空回答规则均是代码行为，不代表用户已决定论文统计时应如何处理未回答样本。运行器默认跳过评估；`summarize_results.py` 只聚合现有布尔标签，并非评分器。

## 4. 现有样本能否充当调参集或独立留出集？

不能据现有证据这样标记。两次归档均覆盖全部 100 个视频和 1,276 个 QA；没有随运行保存的抽样 ID、配置快照或单独日志。代码有 smoke 子集选择器（最多 10 条、按视频与类型确定性抽取），但无法从已保存材料确认这些运行使用过哪些样本。不得把这些全量运行追认为独立留出集。报告记录的源代码提交为 `0e3e419…`，当时工作树有未提交改动，完整执行源码树未冻结。

## 5. 开始评分前还需确认什么，调用量/费用如何估？

仓库没有只对现有 `answers.jsonl` 执行 judge 的专用入口。`run_split.sh --with-eval` / `--glm-eval` 会进入推理流程，不能当成安全的评分专用流程；本次没有运行它们。若只给本地 Control 的非空行各请求一次 judge，预计为 1,270 次基础请求；若选择 Azure，异常重试逻辑最多可能放大到 25,400 次尝试。GLM evaluator 未见同样的重试包装。实际计费、账户额度及部署可用性均未知，未查询也未测试。

进入任何评分执行前，需由用户明确：

1. judge 提供方与确切模型/部署，以及要评哪一个或哪些已有运行；
2. 空回答按错误计、排除，还是单列；异常/无法解析的 judge 输出如何处理；
3. 总请求硬上限和单条重试上限，并在 API 故障时停止而不是继续把故障写成错误答案；
4. 评分仅用于报告，还是会用于后续调参；如用于调参，另行确认样本边界与独立留出方案。当前全量样本不能被默认当作留出集。
