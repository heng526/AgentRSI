# From Failed Trajectories to Reliable LLM Agents: Diagnosing and Repairing Harness Flaws (HarnessFix) (2026, arXiv 2606.06324 v2, 中科院软件所/国科大/天津大学)

## 问题与动机
- agent 可靠性取决于 harness（包裹基座的运行时基础设施：执行环境/工具接口/上下文与记忆/生命周期编排/可观测性/验证/治理七层 ETCLOVG）。失败常源于 harness 如何暴露信息、启用动作、记录证据、执行策略，而非仅模型推理。
- 现有自我改进/自动 harness 演化两条线的缺陷：运行时监督线绕过或临时压制错误而不修根因；结果驱动线按最终分数优化 prompt/工作流，不先定位"失败证据在轨迹哪里、哪个 harness 机制失职"→改进宽泛、间接、scope 差。
- 动机研究：30 个开源 agent 仓库、约 57,780 条开发记录（issue/PR/commit/release notes），harness 相关 26,174 条（45.3%），30/30 仓库都有；七层全有缺陷，Lifecycle/Tooling/Observability 最频繁（29/30 仓库涉及）；从缺陷模式与开发者修复实践归纳出分层修复算子表。

## 方法拆解
- **HTIR（Harness-aware Trace Intermediate Representation）**：把原始轨迹+harness 工件编译为结构化诊断基底——
  - TraceStep（运行时证据单元：id、request/response 消息+派生标注 role/执行状态/artifact-state effect 及其证据）；
  - 数据流链接（跨步信息复用：copied/summarized/semantically reused，含精确 span 切片——使"必需字段缺失"类错误可观察）；
  - 控制流链接（解释 harness 驱动的步转移：continue/retry/delegate/validate/finalize/terminate+触发条件）；
  - 实现锚点（把运行时证据映射回可编辑工件：文件路径行号/prompt 模板/工具 schema/校验器 id，含锚定关系与支持证据）；
  - ETCLOVG 责任层映射（逐轨迹而非静态文件分类）。
- **诊断**：失败归因四步——症状定位→证据回溯（沿数据流/控制流链接反向，产生候选责任步集合，刻意从宽）→候选裁决（判定该步是形成/传播/未暴露/未约束/未验证相关信息或状态）→层归属。输出结构化诊断记录（归因结果+失败信号+harness 诊断）。缺陷合并：跨任务执行合并重复诊断成 flaw record（缺陷摘要+支撑诊断集）——"单次失败可能是偶然，改动前先合并"。
- **Scoped Repair**：缺陷记录→按层选择修复算子（Table II，如 Context/Memory 层：failure-relevant evidence preservation、summary and retrieval policy repair、persistent-memory isolation、context-budget checking；Verification 层：completion-check strengthening 等）→实例化 flaw-specific 修复规范→约束化补丁生成。刻意限制自由编辑（对比 self-improvement coding agent 的自由改写），防不稳定编辑与大面积回归。
- **验证与 Harness Memory**：验证 agent 检查补丁是否在修复范围内、是否降低目标缺陷且无不可接受回归（回归感知验证）；通过验证的补丁与缺陷记录进入 harness 记忆供复用。
- **训练方式**：四个 LLM agent（trace 抽象/诊断/修复/验证）协作，无参数训练；基座完全不动（harness repair=改工件，明确排除改基座参数——与本选题"冻结基座"完全同向）。

## 数据与实验
- 四基准：GAIA、SWE-Bench Verified、AppWorld、Terminal-Bench 2.0 Verified；5 个 LLM。
- RQ1：对初始 harness 平均提升 11.1%（区间 6.3%–18.4%）；GAIA 最大 14.5–18.4%（如 open-deep-research 43.3，+18.4；DeepResearchAgent 52.8，+8.9；MiroFlow 58.3，+3.4）；AppWorld 最小增益 5.9–9.3%；各 LLM 平均增益 10.3–12.5%（模型一致性）。固定 GPT-5 mini 端到端对比：超人类设计 harness 平均 6.3%（1.9–10.0%）且无需人工设计。
- RQ4 跨模型迁移：GPT-5 mini 修复的 GAIA harness 直接复用于 Qwen3.5 Plus、DeepSeek V3.2、Gemini 3 Pro、Claude Sonnet 4.5，迁移增益 5.5%–9.5%（源模型 +18.4%）。
- RQ2 失败诊断分析：GAIA 缺陷集中于 Tool Interface+Observability；SWE-Bench 集中于工具执行×上下文构建×验证证据接口；AppWorld 暴露状态效应模式；Terminal-Bench 压力在 Context/Memory、Lifecycle、Verification、Governance。
- RQ3 消融：trace-grounded 诊断与 scoped repair 是增益关键。

## 创新点
1. 首个 harness 缺陷实证研究（30 仓库/5.8 万记录/七层分布/修复算子表）。
2. HTIR：轨迹级"证据链"中间表示——数据流+控制流+实现锚点把失败证据锚回可编辑工件，实现步骤级归因（诊断模板：症状→宽回溯→严裁决→层归属）。
3. 缺陷合并+算子约束的 scoped repair+回归感知验证——"诊断驱动、范围受限"的自动修复范式，与结果驱动的自由自编辑明确切割。

## 局限
- 修复对象是 harness 工件（代码/prompt/配置），不是记忆内容本身——Context/Memory 层缺陷修的是"记忆组装策略"，不审计记忆条目正确性。
- 依赖可复算的轨迹与环境反馈（benchmark 型验证器），开放任务失败信号弱时诊断链条断。
- 验证需回归测试集；补丁进 harness memory 的跨任务复用只是记录级，未形成策略抽象。
- 修复 agent 本身是 LLM 判断（锚点/归因可能错），错误修复的修复（meta-rollback）未讨论。

## 与本选题关系
- **撞车风险：高（方法论模板层）**。
- **overlap**：HarnessFix 的管线就是"证据驱动错误定位→局部修复"的成熟范例——TraceStep/数据流链接≈我们视频记忆中的证据链溯源；候选宽回溯+严裁决≈我们的多步归因；缺陷合并≈跨任务错误模式沉淀；scoped repair+回归感知验证≈我们的修复约束与修复后验证；且同样以"失败轨迹为结构化证据而非仅反馈信号"立论（摘要原话）、同样冻结基座。其 Context/Memory 层与我们的记忆层直接交叠。
- **difference_from_ours**：对象域不同——它修 harness 工件（代理系统外壳），我们修视频记忆内容与策略（记忆架构内部状态）；其证据链基于文本轨迹+代码工件的可文本对齐，多模态视频证据链（视觉证据何时写入、哪帧支撑哪条记忆、修复需回看哪段）未被处理；无多模态；跨任务维度是 harness 补丁复用而非策略进化。写作策略：必须正面引用并借其"诊断驱动修复"合法性，同时把"从 harness 工件到记忆内容/策略、从文本轨迹到多模态证据链"的两个域移动作为我们的增量。
